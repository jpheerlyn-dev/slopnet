## claude (Opus 5) did

Two separate faults, both mine, both found because the operator sent a picture of Google's error page rather than a description of it.

**The authorisation URL arrived truncated.** Google answered "Access blocked — required parameter is missing: response_type", with the operator's own account named on the page. That combination is the clue: the page could only name the account because `client_id` reached Google, so the URL was not wrong, it was cut. This console tells programs how wide it is, so a program printing a link three hundred characters long has it wrapped by the terminal and it arrives here as several separate lines. The matcher read one line at a time and took the first fragment. Every parameter after the wrap — `response_type` among them — was dropped before the browser ever opened. Lines filling the full width are now rejoined before anything looks for a link, because such a line was wrapped rather than ended.

**Arrow keys were sent in the form the program was not listening for.** A full-screen program turns on application cursor key mode and from then on expects an arrow as `ESC O A`, not `ESC [ A`. The parser recognised the mode escape and threw it away with the rest of the private modes, so we kept sending the wrong one. Enter worked throughout, which is what made this look like a partial failure rather than a mode difference: carriage return is the same byte either way. The mode is now tracked, and `sendKey:` picks the form the running program expects — the entry view no longer decides, because a text box has no business knowing about terminal modes.

Both faults were live in v0.9.31, which I reported as shipped and working. The keys probe I wrote for it called `sendKeys:` with the bytes already chosen, so it could not have caught either one — it tested my assumption rather than the behaviour. It now drives real programs in both modes and checks the exact bytes that arrive, including that hiding the cursor does not disturb them.

While proving the first fix my own probe mangled the URL: I passed it as bash `printf`'s format string, so `%3A%2F%2F` was read as float specifiers. The probe was wrong, not the console. Data is now an argument, never a format.

## claude (Opus 5) did — second pass

The operator sent a photograph of the menu walking down the screen, and it carried the diagnosis: the hint line read `> se arrow keys to navigate` — its first two characters overwritten — and the selection *had* moved when they pressed down. Keys were arriving. This was the console failing to draw what came back.

A menu redrawing in place has to put the cursor back where the old frame started. There are three usual ways to write that and the console understood one. `ESC 7` and `ESC 8` — remember the cursor, come back to it — carry no bracket, and the parser's final branch stepped over any such escape one character at a time and discarded it. So the program said "go back to the top of the menu", the console heard nothing, and every frame landed below the one before it, each leaving its prompt marker behind. `ESC M` was going the same way.

Rather than guess which sequence Antigravity uses, `tests/menu_fixture.py` draws the same two-item sign-in menu three ways — cursor up, save and return, and a full-screen program redrawing from the top — and the probe presses down then up and checks the screen holds one menu with one marker on the first item. Only the middle style failed before the fix, which is how I know the probe can see the defect rather than agreeing with me.

Found while there: `ESC [ H` threw away both its parameters, so every absolute move went to the same corner; rows in an absolute move were counted from the top of the whole session rather than the top of the screen; and erase-in-line ignored which part of the line it was asked to erase. Also added the next/previous line moves and row-absolute.

The tile said "Gemini" while installing Antigravity. It says Antigravity now, in the tile and the wizard both.
