## claude (Opus 5) did

Two separate faults, both mine, both found because the operator sent a picture of Google's error page rather than a description of it.

**The authorisation URL arrived truncated.** Google answered "Access blocked — required parameter is missing: response_type", with the operator's own account named on the page. That combination is the clue: the page could only name the account because `client_id` reached Google, so the URL was not wrong, it was cut. This console tells programs how wide it is, so a program printing a link three hundred characters long has it wrapped by the terminal and it arrives here as several separate lines. The matcher read one line at a time and took the first fragment. Every parameter after the wrap — `response_type` among them — was dropped before the browser ever opened. Lines filling the full width are now rejoined before anything looks for a link, because such a line was wrapped rather than ended.

**Arrow keys were sent in the form the program was not listening for.** A full-screen program turns on application cursor key mode and from then on expects an arrow as `ESC O A`, not `ESC [ A`. The parser recognised the mode escape and threw it away with the rest of the private modes, so we kept sending the wrong one. Enter worked throughout, which is what made this look like a partial failure rather than a mode difference: carriage return is the same byte either way. The mode is now tracked, and `sendKey:` picks the form the running program expects — the entry view no longer decides, because a text box has no business knowing about terminal modes.

Both faults were live in v0.9.31, which I reported as shipped and working. The keys probe I wrote for it called `sendKeys:` with the bytes already chosen, so it could not have caught either one — it tested my assumption rather than the behaviour. It now drives real programs in both modes and checks the exact bytes that arrive, including that hiding the cursor does not disturb them.

While proving the first fix my own probe mangled the URL: I passed it as bash `printf`'s format string, so `%3A%2F%2F` was read as float specifiers. The probe was wrong, not the console. Data is now an argument, never a format.

The operator sent the terminal itself this time rather than a photograph of it, and the answer was in the third row of Antigravity's sign-in box: a row far wider than the box, carrying fragments of earlier frames inside it.

This console told programs how wide it was and then did not wrap at that width. A terminal moves to the next row when a line reaches the right edge, and programs count on it — they print a long line and then move the cursor back up by the number of rows they expect it to have taken. Every long line printed here stayed on one row, so the program's arithmetic and this console's parted company, and each redraw landed somewhere the last one had not been. That is the whole of it: the shredded box, the interleaved fragments, and an authorisation URL cut off at the end of its first row. The two earlier passes were both real faults, but this one was underneath them.

Wrapping now happens on the character after the edge is reached rather than on reaching it, so a panel exactly the width of the window does not gain a blank row beneath every line.

The link reassembly written yesterday assumed rows are the full width of the window. Antigravity splits the link itself and pads it inside a box, so those rows are short and the padding is not part of the link — the rule now is that a row of nothing but link characters continues the row above it, and a space, a box rule or a blank row ends it. A run of ordinary words cannot be swallowed into a URL because a space breaks the chain. Both shapes are checked: one this console wrapped, one the program wrapped into a box.

Also raised the window searched for a link from twelve rows to twenty-four. Antigravity's box is thirteen rows on its own, so the old window could begin part-way down the link and take a fragment for the whole of it.

## claude (Opus 5) did — fourth pass

Three browser windows opened at once, each carrying a link broken a different way, and Google named the damage precisely: "OAuth 2 parameters can only have a single value: scope". I had been reading the link off the drawn screen and rebuilding it. That was the mistake, and the last three passes were all refinements of it.

A program redrawing a frame writes over part of what is already there. A drawn row therefore holds pieces of two or three frames at once, and no rule for rejoining rows can recover a link from that — the pieces are genuinely interleaved. Each pass I improved the rebuilding and got a differently-wrong link. What the program *wrote* is not damaged in that way, so the console now keeps a copy of it with the escape sequences removed and nothing moved, and reads the link from there. The drawn screen is for the person; the stream is for the machine.

Two guards behind it, because a rebuilt link should not be trusted on its own. A link whose query carries the same parameter twice is a link that was rebuilt wrongly, so it is not offered at all — that single test rejects every one of the three that were opened. And only one authorisation page is offered per run, so a second reading cannot open a second window.

Separately, the box rules came out as rows of "â". A read stops wherever it stops, which can be halfway through a character; decoding that as UTF-8 fails, and this fell back to Latin-1 for the whole read, mangling the rest of the chunk along with it. Leftover bytes now wait for the ones that finish them. Four bytes is the longest character, so anything still undecodable after trimming that many is genuinely not UTF-8 and keeps the old fallback.

Evidence: prompt probe 36, including a boxed link redrawn over itself — offered once, matching what the program printed — and a link with a repeated parameter refused. Menu 11, keys 4, scroll 6, grow, striped, wizard, crew, six checks, app builds.

Not proved: still no completed sign-in. Four passes. The first three each fixed something real but all three were downstream of reading the screen instead of the stream, which is why every fix produced a new variety of the same failure rather than ending it. I should have moved to the stream at the first sign that reassembly was guesswork.

## claude (Opus 5) did — fifth pass

The operator refused the conclusion I reached last time, and they were right to. I had said Google was refusing Antigravity's own configuration and there was nothing to do about it. That was wrong, and I reached it by reasoning from two GitHub issues instead of from this software.

What settled it: I captured the exact bytes `agy login` writes on the server, took the link out of that capture by hand, and fetched it. Google showed an ordinary sign-in page. So the link Antigravity prints is fine, and the one SlopNet opened was not.

Replaying the capture through the console showed why, and it depends on something no invented fixture would have varied — how the reads happen to be cut up. Delivered whole, the console found the right address. In 4096-byte pieces it found a truncated one, re-encoded into nonsense by NSURL because it ended inside a percent escape: `%3A` became `%253A`. In 1024-byte pieces, truncated at the challenge. In 137, truncated after four parameters. The console was reading the link the moment part of one appeared, and the one-per-run guard added in the previous pass then held on to that half-written address while the whole of it arrived milliseconds later. That guard turned an intermittent fault into a reliable one.

An authorisation link is now offered only once the program has stopped writing for four hundred milliseconds. Nothing cheaper is sound: a link arrives in pieces, and a program redrawing its frame prints more after every piece, so at any moment mid-write the longest thing resembling a link may be half of one. Alongside that: a row carrying its own scheme starts a link rather than continuing the row above it, an address containing two schemes was spliced from two copies and is refused, an address NSURL had to rewrite to accept is refused, and the longest copy wins over a half-written newer one.

Four of the fixtures I wrote for this bug were guesses at what Antigravity prints. One of them passed with the fix removed — it never reproduced anything. `tests/agy_login_recording.bin` is the real output, kept in the repository with the script that captured it, and `console_replay_probe` replays it whole and in three sizes.
