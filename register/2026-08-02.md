## 04:36 — opus 5 did — uninstall could never remove its own key

The operator asked for a clean wipe of both machines so first-run setup could
be tested honestly. `reset-for-testing.sh --all` refused at the first step,
and the reason turned out to be a bug rather than a bad key.

`ssh-keygen -y` prints the private key's comment on some OpenSSH builds and
leaves it off on others. This Mac runs OpenSSH 10.2, which prints it. The
uninstaller compared the whole line against the derived key with
` slopnet-vps` appended, so it was matching a three-field line against a
four-field one and always concluding that SlopNet's own key was untrustworthy.
It then declined to use the key, fell back to a password, and could not take
the key off the server. `slopnet-vps-onboard.sh` was fixed for exactly this
before, with a comment saying so; removal and the local SSH proof were not.
Both now compare key material only, as onboarding does.

Second stop, and the safety machinery working as intended: `userdel` refused
because a slopnet-owned process was still alive, and the uninstaller removed
nothing rather than forcing it. The process was transient and gone a moment
later; nothing slopnet-owned and no service was running when checked.

The wipe then completed. On the server: the private account and its files,
/opt/slopnet, and only the receipt-backed key from the login account's
authorized_keys. On this Mac: the connection key, the proved fingerprint file
and the remembered settings. SlopNet.app was removed from Applications.

Proved: checks/shell-syntax.sh and both scripts parse; the wipe ran end to
end and this Mac reads as a machine that has never run SlopNet. Not proved:
setup itself, which is what the operator is about to test.

that was my error rather than a fault in the machinery.

the pinned tag and requires it to resolve to that same commit. A branch head
never equals a tag's commit, so step 3 refused every time and changed nothing.

tag; I read it as "the server gets the released code" rather than "setup

this branch, so the app can be built on the released path — baked commit equal

## 13:20 — opus 5 did — safe_marker was destroying the caller variable

The local guide refused with "The server install does not match its protected
ownership receipt" on every attempt. It was not stale state and not the
server: it is a bug in the released server scripts, and it makes the local
guide, project, build and coding-app flows impossible to complete.

safe_marker took its arguments as marker and expected. sh has no local
variables, so the assignment to expected overwrote the caller variable of the
same name, which holds the resolved release commit. Two lines later
install_receipt was handed that wreckage instead of a commit and built a
receipt whose commit field contained an entire runtime-account receipt. It
could never equal what onboarding had written, so the check refused every
time, in the same way, forever.

The arguments are marker_path and marker_want now, in all five scripts that
carry the function.

Found by extracting the payload from the installed app, running its
verification block against the real server, and printing the computed and
stored receipts side by side. Guessing from the source had already produced
two wrong answers before that.

Also recorded because it cost a build: the payloads are one long
single-quoted string, so a comment containing an apostrophe closes it. That
was done here for the second time today. Both fixed comments now say so at
the top of the block.

Proved: all seven checks/*.sh; the repaired verification block run against
the live server, which now passes every gate; app rebuilt on the released
path with the baked commit matching the tag.

## 13:55 — opus 5 did — the local guide proof was a coin flip

The local guide installed Llama.cpp, downloaded the model, loaded it and
generated an answer, then refused: "The local model did not answer its
one-time harmless challenge."

The challenge asked a 3B model to print a 24 character hex string with its
characters reversed. It cannot do that. Measured against the shipped default
on the operator server, reversing scored 0 of 3 even after shortening the
token to 8 characters. So the gate was close to a coin flip, and it was
failing installs where nothing was wrong at all.

It now asks for the token in capital letters, which the same model got right 3
of 3, and the whole repaired block was then run end to end against the real
model three more times: 3 of 3. The proof still shows the model loaded, read
the prompt and generated from it. It cannot be satisfied by the prompt being
echoed back, because the token is regenerated until it carries a letter and
the prompt shows it in lower case. The comparison is contains rather than
whole-line, because the chat front end wraps the answer in its own framing and
an exact line match rejected correct answers.

Worth stating plainly, since it came up: this predates the look-and-feel work.
The challenge is present verbatim in v0.9.61 and was written in 8b81770. The
only change the visual pass made to this file was renaming the safe_marker
arguments.

Proved: all seven checks/*.sh; payload extracted and parsed; the repaired
proof block run three times against the real model on a real server, passing
each time. Not proved: the wizard driving it end to end, which is next.
