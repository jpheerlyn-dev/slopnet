# Parked: look, feel, and onboarding

Operator brief, 2026-07-30. **Parked — not started.** Nothing here is to be
built until the operator says so.

Recorded because a spoken brief is lost by the next session, and because two
points below conflict with earlier decisions that were just as explicit. Those
conflicts are flagged, not resolved: resolving them is the operator's call.

## 1. The illusion stops at the console

The PTY has the StormCode palette. The wizard and Settings do not — they are
default AppKit, so they read as an office app bolted to a terminal.

Wanted: one dark, high-contrast theme across the whole app.
`NSWindowStyleMaskFullSizeContentView` and a dark appearance to lose the
standard title bars; monospaced type and terminal-shaped fields in the wizard.

Current state: no `NSAppearance` and no `FullSizeContentView` anywhere in
`packaging/*.m`. The console draws its own colours; every other surface takes
the system default. So this is unstarted, not half-done.

## 2. Context switching during setup

Sending somebody to a raw Terminal for SSH keys or a sudo password breaks the
experience for the audience this is for.

Wanted: key generation and password prompting handled inside the GUI.

Current state, so this is scoped honestly rather than from the brief alone:
keys are already generated by `slopnet-vps-onboard.sh` running inside the app's
own console, and password and yes/no prompts already have native controls
(`SlopNetPrompt`, the prompt bar). The gap is narrower than "drop into
Terminal" — it is the wording. Three places in `SlopNetWizard.m` (lines 270,
319, 345) say "the window behind this one", which describes the sheet sitting
over the console and reads like a different application. Worth checking what
actually remains outside the GUI before building anything.

## 3. Jargon in the wizard

`ibm-granite/granite-4.1-3b-GGUF:Q4_K_M` and SSH port numbers are too much for
a beginner.

Wanted: presets and dropdowns instead of typed strings.

Current state: the model is already a constant (`kDefaultGuideModel`) and is
shown rather than typed, but it is shown *as that string*. The friction is that
it is displayed at all, not that it must be entered.

## 4. Scaffolding for the Granite translator — WITHDRAWN

The operator has since ruled this out: "Do NOT do any split screen layouts —
keep the chat UI with left side panel — the chat terminal IS the hacker
terminal." The single-window design stands. Kept below only so the conflict is
not rediscovered and re-argued later.


Wanted: a split pane or overlay — terminal on one side, plain-English
translation streaming alongside.

**This contradicts an earlier decision.** The operator previously said, in
these words: "No — Keep the terminal style chat window without splitting
anything... the terminal output should appear directly inside of the chat
window and the IBM model sees that as conversation history, and takes control
of the terminal for the user... It should all be inside that one terminal
window — That's why I designed all those colours and logos and stuff."

The current single-view design was built to that instruction. Both readings are
coherent; they are not compatible. Which one stands is a decision, and it wants
making before any UI restructuring, because the two lead to different
architectures.

A second, smaller conflict: point 1 asks for the whole app to feel like the
terminal, while point 4 asks for a separate plain-English pane beside it. That
is resolvable — the translation pane can carry the same palette — but it is
worth being deliberate about, since the plain-English half exists precisely to
be *unlike* a terminal for somebody who finds terminals frightening.
